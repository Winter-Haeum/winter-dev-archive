# Winter Dev Archive Document Generation Policy

이 문서는 Winter Dev Archive의 모든 학습 문서에 공통 적용되는 기본 정책입니다.

이후 생성되는 모든 Step / Lesson 문서는 별도 요청이 없어도 아래 규칙을 자동 적용합니다.

---

## 작업 규칙

1. 원문 내용 절대 삭제 금지
2. 예제 코드, 주의사항, 강사 코멘트 모두 유지
3. 원문 순서 최대한 유지
4. Winter Dev Archive 문서 형식 적용
5. 부족한 내용은 초보자 기준으로 필요한 경우만 보충
6. markdownLoader.js frontmatter 규칙 준수
7. 최종 결과는 바로 저장 가능한 Markdown(.md) 형태
8. 원문 명령어, 코드, 스크립트는 수정하거나 축약하지 말 것
9. 원문에 없는 내용을 추가할 수 있으나 원문을 대체하거나 왜곡하지 말 것
10. 원문이 이미 충분한 경우 불필요한 재설명이나 재요약 금지
11. 원문에 포함된 표, URL, 이미지 설명도 유지
12. 본문 하단에 "다음 단계", "다음 문서" 안내는 작성하지 말 것
13. 단순 나열형 정보(UI 요소, 용어 정리, 비교 항목 등)는 가독성을 위해 표 형태로 재구성 가능
14. 표로 변경하더라도 원문 내용은 100% 포함
15. 실습형 문서는 인터랙티브 데모 영역 추가 가능
16. 체크포인트는 실제 체크 가능한 형태를 고려 (`- [ ]`)
17. 한국어 문서 가독성을 고려하여 단어가 어색하게 줄바꿈되지 않도록 구성

---

## 문서 구조

모든 문서는 가능한 동일한 구조를 사용한다.

아래 구조는 AI가 보충하는 섹션의 표준 형식이며, 원문에 이미 제목이 있는 섹션은 원문 제목을 그대로 유지한다.

```
# 제목

## 🎯 학습 목적

## 📖 개념 설명

## ⚙️ 동작 원리

## 💻 예제 코드

## ⚠️ 주의사항

## 📝 핵심 정리

## 🔗 참고 자료

## ✅ 체크포인트
```

원문에 없는 섹션은 필요 시 생략할 수 있다.

아래 표준 제목은 원문의 같은 의미 섹션에도 동일하게 적용하여 전체 문서 스타일을 통일한다.

| 원문에서 자주 쓰는 표현 | WDA 표준 제목 |
|------------------------|--------------|
| 학습 목표, 이 수업에서 배울 것 | `## 🎯 학습 목적` |
| 개념 설명, 이론, 실습 개요 | `## 📖 개념 설명` |
| 동작 원리, 내부 구조 | `## ⚙️ 동작 원리` |
| 예제 코드, 코드 예시 | `## 💻 예제 코드` |
| 주의사항, 주의 | `## ⚠️ 주의사항` |
| 정리, 요약, 핵심 | `## 📝 핵심 정리` |
| 참고 자료, 링크 | `## 🔗 참고 자료` |

단, 원문에 고유한 섹션 제목이 있고 표준 제목으로 대체하면 문맥이 어색해지는 경우에는 원문 제목을 유지한다.

---

## 문서 디자인 시스템

- Step과 Lesson은 동일한 UI와 섹션 스타일을 사용한다.
- 문서마다 제목 스타일이 달라지지 않도록 한다.
- 코드와 명령어만 코드 블록을 사용한다.
- 일반 설명문은 불필요하게 코드 블록으로 감싸지 않는다.
- 단, 원문이 일반 설명문을 코드 블록으로 표현한 경우 원문 형식을 유지한다.
- 현재 작성된 문서와 앞으로 생성될 문서 모두 동일한 스타일을 유지한다.

---

## 원문 보존 원칙

가장 중요한 원칙은 **원문 100% 보존**이다.

- 원문 내용을 삭제하지 않는다.
- 원문 제목을 임의 변경하지 않는다.
- 원문을 AI가 다시 자기 말로 요약하지 않는다.
- 디자인 개선은 가능하지만 원문을 대체하지 않는다.

원문 보존 원칙이 문서 구조 규칙보다 우선한다.

---

## 향후 작업 방식

이 문서는 Winter Dev Archive의 공식 문서 생성 정책이다.

앞으로는 아래 형식으로만 요청해도 이 정책을 자동 적용하여 문서를 생성한다.

```
저장 위치:
content/[카테고리]/[섹션]/[파일명].md

[원문 붙여넣기]
```

별도의 작업 규칙을 다시 입력하지 않아도 된다.

---

## 문서 표현 방식 원칙

Winter Dev Archive는 단순 원문 보관소가 아니라 **디지털 참고서 + 실습 교안**을 목표로 합니다.

AI는 원문 내용을 100% 유지하는 것을 전제로, 가독성과 학습 효과를 높이기 위해 자유롭게 레이아웃을 재구성할 수 있습니다.

18. 원문 내용(문장, 코드, 명령어, URL, 주의사항, 강사 코멘트)은 100% 유지한다.
19. 원문 내용을 삭제하거나 축약하지 않는 범위에서 가독성을 높이기 위한 UI 재구성을 허용한다.
20. 단순 나열형 정보는 상황에 따라 다음 형태로 변경할 수 있다.
    - 표(Table)
    - 카드(Card)
    - 단계형 카드(Step Card)
    - 타임라인(Timeline)
    - 비교 박스
    - 인터랙티브 데모
    - 체크리스트
    - 플로우 다이어그램
21. 문서 작성 중 사용된 단순 번호 체계(예: 2-1, 2-2, 3-1)는 반드시 유지할 필요는 없으며, 더 좋은 구조가 있다면 자유롭게 재구성할 수 있다.
22. 코드블록(text 박스)은 실제 코드, 명령어, 프롬프트, 복사해서 사용해야 하는 내용에 우선 사용한다. 일반 설명 문장은 가능한 한 일반 본문, 표, 카드 UI 등으로 표현한다.
23. AI는 원문을 단순 복사하는 것이 아니라, 학습자가 한눈에 이해할 수 있는 디지털 참고서 형태로 문서를 구성한다.
24. 기존에 등록된 모든 문서와 앞으로 생성되는 모든 문서에도 동일한 정책을 적용한다.
25. Winter Dev Archive는 단순 Markdown 문서가 아니라, **디지털 참고서 + 다이어리 스타일의 교안 웹**을 목표로 한다. 전체 문서가 한눈에 읽히고, 학습 흐름이 자연스럽게 이어져야 한다.
26. AI는 카드, 타임라인, 단계형 UI, Callout Box, 비교 카드, 완료 배너 등 다양한 시각화 컴포넌트를 적극 활용하여 문서를 구성할 수 있다.
27. 긴 설명문은 가능한 한 시각적으로 분절하여, 정보를 단번에 파악할 수 있도록 레이아웃을 구성한다.
28. **"읽고 싶은 교안"**을 최우선 기준으로 삼는다. 텍스트 나열보다 시각적 구조화가 학습 효과를 높인다.
29. 이 원칙은 신규 문서뿐만 아니라 기존에 등록된 모든 문서에 동일하게 적용한다.
30. 단순 번호 체계(1-1, 2-1, 3-1 등)는 학습 구조를 이해하는 데 꼭 필요하지 않다면, 시각적으로 더 읽기 좋은 카드·단계 번호(①②③)·타임라인 등으로 재구성할 수 있다.
31. AI는 단순히 안전한 변경만 하는 것이 아니라, Winter Dev Archive의 디자인 철학(디지털 참고서 + 다꾸 스타일 교안)에 더 적합한 방향을 우선 선택한다.
32. 단계형 설명이나 프로세스 설명은 가능하면 플로우 카드, 타임라인, 단계 카드 등을 우선 활용한다.
33. 원문의 "다음 단계", "다음 문서" 안내는 본문에서 제거할 수 있지만, "이론 학습 완료", "실습 완료" 같은 학습 완료 메시지는 반드시 유지한다.
34. 기존 문서를 포함한 전체 Winter Dev Archive에서 단순 내부 번호 체계(1-1, 1-2, 2-1 등)는 특별한 학습 구조상 필요하지 않다면 제거하고, 단계 카드·①②③ 번호·타임라인·플로우 카드 등 WDA 디자인 철학에 맞는 표현으로 통일한다. 문서마다 번호 표현 방식이 혼재되지 않도록 전체 일관성을 최우선으로 유지한다.
35. 단순 번호 체계(1-1, 1-2 등)를 제거하는 경우, AI는 학습 흐름이 끊기지 않도록 다음 중 하나 이상의 방식으로 하위 구조를 명확하게 표현한다: ①②③ 단계 번호 / STEP 카드 / 아이콘 + 섹션 제목 / 플로우 카드 / 타임라인. 번호를 제거한 자리를 단순 텍스트 제목만으로 남겨두지 않는다.
36. 단순 명령어(1~2줄)는 불필요하게 큰 코드블록으로 표현하지 않고, 인라인 코드 또는 소형 카드 형태를 우선 사용한다.
37. 설치 과정이나 절차형 설명은 가능하면 플로우 다이어그램, 단계 카드, 타임라인 등을 우선 활용한다.
38. 시각적으로 더 읽기 좋은 구조가 가능하다면 단순 텍스트 나열보다 다이어리형 정보 디자인을 우선 선택한다.
39. 플로우(절차)형 내용은 세로 배치로 고정하지 않는다. 가독성과 화면 공간을 고려하여 가로 플로우 카드, 세로 타임라인, 단계 카드 등 가장 적합한 레이아웃을 선택한다.
40. PC와 모바일 환경을 고려하여 가로 배치가 어려운 경우에는 자동으로 세로 배치가 가능한 구조(flex-wrap: wrap)를 우선한다.
41. 동일한 카드 레이아웃이나 정보 표현 방식이 한 문서 안에서 과도하게 반복되지 않도록 한다.
42. AI는 정보의 성격에 따라 카드, 메모 카드, 비교 카드, 표(Table), 플로우 다이어그램, 단계 카드, 타임라인, 색상 샘플, Callout, 완료 배너 등을 적절히 조합하여 시각적 리듬감을 만든다.
43. 같은 아이콘 카드 패턴이 연속으로 반복될 경우, 더 적합한 표현 방식이 있다면 다른 정보 디자인으로 변경할 수 있다.
44. Winter Dev Archive는 단순히 "잘 정리된 문서"가 아니라 "계속 읽고 싶고, 넘겨보고 싶은 디지털 참고서 + 다꾸 교안"을 목표로 한다. AI는 안전한 변환보다 더 읽기 좋은 정보 디자인을 우선 선택할 수 있다.
45. 같은 문서 안에서 카드 → 카드 → 카드처럼 동일한 패턴이 반복되지 않도록 하며, 필요하다면 카드 → 메모 → 비교표 → 플로우 → 타임라인 등으로 표현 방식을 적절히 변화시켜 읽는 흐름에 리듬감을 만든다.

## 콘텐츠 표현 원칙

1. 동일한 UI 컴포넌트(Table, Card, Callout, Code Block 등)를 목적 없이 과도하게 반복하지 않는다.
2. 같은 컴포넌트 유형이 2회 이상 연속으로 등장하지 않도록 한다. 연속 배치가 불가피할 경우 명확한 이유가 있어야 한다.
3. **학습 목표(학습 목적)는 비교 데이터가 아니므로 Table보다 Card 또는 Callout을 우선 사용한다.** 학습 목표는 독자가 문서를 펼쳤을 때 가장 먼저 읽는 영역이므로 시각적으로 명확하게 강조되어야 한다.
4. 콘텐츠의 성격에 맞는 UI를 선택하여 Visual Hierarchy(중요도 순서)와 Visual Rhythm(읽는 흐름의 리듬감)을 함께 유지한다.
5. "디자인 일관성"을 이유로 모든 섹션을 같은 형식으로 만들지 않는다. 가독성과 학습 효율이 항상 형식 일관성보다 우선한다.
6. 문서를 검토할 때 "연속된 표", "연속된 카드 박스", "연속된 Callout", "반복 패턴"이 있는지 확인하고, 시각적 단조로움이 느껴지면 변경을 검토한다.

## 기존 문서 리팩토링 정책

새로운 디자인 정책은 신규 문서뿐만 아니라 기존에 작성된 모든 문서에도 동일하게 적용된다.

- 모든 페이지를 순차적으로 검토하여 현행 정책에 맞지 않는 부분을 찾아 수정한다.
- 단순히 컴포넌트 종류를 교체하는 것이 아니라, 전체 흐름과 가독성을 고려한 리팩토링을 수행한다.
- 리팩토링 시 콘텐츠는 100% 보존하며, 삭제 또는 요약 축소 없이 표현 방식만 변경한다.
- 디자인 시스템은 지속적으로 발전하는 것으로, 일회성 작업이 아닌 반복 검토·개선 사이클을 따른다.

### 리팩토링 후 체크리스트

- □ Table 과다 사용 여부 (연속 3개 이상이면 재검토)
- □ Callout 과다 사용 여부 (연속 3개 이상이면 재검토)
- □ Card(fgrid) 과다 사용 여부 (연속 2세트 이상이면 재검토)
- □ 반복 레이아웃 여부 (동일 패턴의 섹션이 연달아 등장하는지)
- □ Visual Rhythm (읽는 흐름에 리듬감이 있는지)
- □ Visual Hierarchy (중요한 정보가 시각적으로 더 강조되는지)
- □ 학습 효율 및 가독성 (처음 보는 독자도 쉽게 읽을 수 있는지)

## frontmatter 규칙

모든 문서는 아래 형식의 frontmatter를 포함한다.

```yaml
---
title: "제목"
date: "YYYY-MM-DD"
status: "draft" | "in-progress" | "review" | "completed"
description: "한 줄 설명"
---
```

- `status` 기준: 작업 시작 전 `draft`, 작성 중 `in-progress`, 검토 중 `review`, 완성 `completed`
- `date`는 문서 작성일 기준

## 스티커 & 데코레이션 디자인 시스템 정책 v3.4

### 0. 최우선 원칙 — 가독성 절대 우선

> **"스티커를 붙인 예쁜 학습 노트"이지, "스티커 때문에 글씨가 가려지는 노트"가 아니다.**

이번 작업 목표는 "데코를 많이 붙이는 것"이 아니다.
**"실제 다꾸 노트처럼 자연스럽고 읽기 편한 교안"** 을 만드는 것이 목표다.

- `padding-left: 캐릭터 width + 40px` 이상 필수
- 텍스트 시작선보다 안쪽 진입 금지

### 6-A. 소형 데코 텍스트 보호구역 ★ (v3.2 신설)

> **소형 데코도 텍스트를 가려선 안 된다.** 제목뿐 아니라 본문 문장·목록·코드블록·표 영역도 침범 금지.

**규칙:**
- 소형 데코(전구·별·꽃·하트·반짝이 등 모든 소형 아이콘)는 텍스트 bounding box 기준 **최소 20~30px 거리** 확보 필수
- 글자 위에 걸치는 배치 절대 금지
- 텍스트 근처보다 **빈 여백 우선** 사용
- 위반 발견 시 처리 순서:
  1. **이동** — 빈 여백으로 이동
  2. **크기 축소** — 더 작게 만들어 회피
  3. **방향 변경** — top/left/right 조정으로 회피
  4. **제거** — 위 세 가지 모두 불가 시 최후 수단

**텍스트 겹침 판단 기준 (Puppeteer QA):**
- 소형 데코 bounding box와 텍스트 element bounding box가 20px 이내로 근접 → 경보
- 두 bounding box가 실제 겹침 → 자동 실패

### 11. 제거보다 이동 우선 원칙 ★ (v3.1 신규)

문제 발견 시 처리 순서:

1. **이동** — 다른 위치로 이동 가능한지 확인
2. **크기 조정** — 더 작게 만들어서 해결 가능한지 확인
3. **방향 변경** — left↔right 방향 전환으로 해결 가능한지 확인
4. **제거** — 위 세 가지 모두 불가능할 경우만 제거

> **삭제는 최후 수단이다.** 기존 데코를 과하게 삭제하지 않는다.

- 수치(개수)를 먼저 맞추는 것이 아니라 **실제 렌더링 분위기**를 기준으로 판단한다.

### 16. 챕터 편차 제거 규칙 ★ (v3.4 신설)

> **특정 챕터만 과하게 비거나 과하게 꾸며지는 현상을 방지한다.**

- 챕터 간 시각적 완성도 편차를 최소화한다.
- 데코가 거의 없는 챕터와 가득 찬 챕터가 공존하는 상태는 실패 판정.
- 전체 문서를 하나의 다꾸 노트처럼 일관된 스타일로 유지한다.
- 편차 해소 방향: 부족한 챕터를 기준 챕터 수준으로 **채운다** (기준 챕터를 줄이지 않는다).

### 17. 빈 공간 활용 규칙 ★ (v3.4 신설)

> **이미지·박스 주변의 과도한 여백에 스티커를 자연스럽게 채운다.**

- 이미지 또는 박스 주변에 넓은 여백이 발생하면 소형 데코 또는 스탬프를 활용하여 채운다.
- 단순 모서리 배치가 아닌 **실제 스티커를 붙인 것 같은 배치** 우선:
  - 약간의 각도(±5~18deg) 적용
  - 박스 경계에 살짝 걸치는 배치 허용 (텍스트 침범 금지)
  - 여러 개를 흩뿌리듯 자연스럽게 배치
- 단, 텍스트·이미지 핵심 내용은 절대 가리지 않는다.
- 지나치게 한쪽 가장자리로만 몰리는 배치 금지 — 5구역 분산 유지.
